# 室設單檔計算機產生器

南應室設 115-1「設計運算與 AI 整合應用」第一堂（2026-09-19）黑克松產出。
把 README Part 3 的題目固化成可重複的流程：需求進去，能跑的工具出來。

## 這個 skill 在做什麼

室內設計的估算有個共同結構：**幾個現場量到的數字 → 一條有假設的公式 → 一個要拿去下單的數量**。
每次重寫網頁很浪費，但每次的公式、單位、損耗率都不一樣。
所以固化的是流程與驗收標準，不是公式本身。

## 硬性輸出規格

產出的檔案必須同時滿足下面五條，缺一條就是沒做完：

1. **單一 HTML 檔**：HTML＋CSS＋JS 全部內嵌，不連任何 CDN。雙擊就能開，工地沒網路也能用。
2. **顯示計算過程**：不能只吐一個答案。每一步的中間值都要列出來，因為這個數字要拿去跟業主或工班對話，對方會問「怎麼算的」。
3. **假設要看得見而且可改**：塗佈率、損耗率、打摺倍數這類會因廠商而異的參數，一律做成可修改的輸入欄，並在旁邊標示預設值的來源。不准寫死在程式裡。
4. **內含驗算區**：頁面底部固定放一組「已知輸入 → 應得答案」的測試案例，載入時自動跑，畫面上顯示通過或失敗。這是 README「agent 會錯，任何產出都要親自驗」的落實方式。
5. **手機可用**：工地是用手機開的。單欄排版，輸入框夠大。

## 流程

### 第 1 步：把需求問清楚（對應「給情境」原則）

動手前先確認四件事，缺哪一項就直接問，不要猜：

- **要算出什麼**：最終要的是公升數？片數？碼數？還是金額？這決定輸出單位。
- **現場能量到什麼**：使用者手上真正有的數字（坪數？牆長？窗寬？），不要設計一個需要他去現場重量的輸入。
- **哪些參數會變**：塗佈率、幅寬、損耗率——這些做成輸入欄。
- **驗算案例**：請他給一組「我知道答案」的實例。沒有這組數字，第 4 步的驗算區就是假的。

### 第 2 步：先寫公式，再寫程式

在 `references/公式與單位.md` 查是否已有這類計算。有就沿用並補充，沒有就新增一節，格式照既有的寫：列出公式、每個參數的意義、預設值、以及預設值的**來源與適用範圍**。

公式寫下來之後先用第 1 步拿到的驗算案例手算一次。**手算對不上就不要開始寫程式**——這時候錯的是公式，寫成網頁只會把錯誤包得更漂亮。

### 第 3 步：套範本產出

以 `templates/計算機範本.html` 為骨架，替換輸入欄、計算函式、驗算案例三處。範本已經滿足上面五條規格，不要從零開始寫。

檔名用中文描述性命名（例：`油漆用量計算機.html`），放在當次上課的個人資料夾底下。

### 第 4 步：親自驗（對應「agent 會錯」原則）

三件事都做完才算通過：

- 用瀏覽器實際打開，確認驗算區顯示通過。
- 手動輸入一組跟驗算案例不同的數字，確認結果合理（量級對不對、改一個輸入答案會不會跟著動）。
- 縮到手機寬度看排版有沒有爛掉。

驗算區顯示失敗時，先確認是公式錯還是程式錯，不要直接改測試案例去迎合程式——那是把溫度計砸了。

### 第 5 步：留痕（對應「可追溯」原則）

截一張跑起來的圖存同資料夾，commit 進 repo。commit 訊息寫清楚這個計算機算什麼、用了什麼假設。

## 邊界

- **這個 skill 產出估算工具，不產出報價單**。要正式報價單走 `interior-boq-quote`，那邊有單價庫和格式規範。
- **算出來的數字是估算，不是下單量**。範本的輸出區已固定加註這句話，不要拿掉。
- **業主的平面圖、地址、姓名不准寫進產出的 HTML**。這些檔案會 commit 進公開 repo。

## 常見陷阱

**輸入欄的 id 不要取跟瀏覽器內建物件同名的字。**
`open`、`name`、`top`、`status`、`length`、`location`、`history` 這些在 `window` 上已經存在，
直接用 `open.value` 取值會拿到內建函式而不是輸入框，算出來整頁 NaN。
範本已改用 `document.getElementById()` 明確取值，沿用即可，不要改回裸寫 id。

**只驗公式的測試會漏掉接線錯誤。**
2026-09-19 實際踩到：公式測試兩組全過，但畫面全是 NaN——因為測試自己建輸入物件，
根本沒經過讀取輸入欄那段。所以範本的驗算區固定放兩種檢查：
一個驗公式（算得對不對），一個驗畫面（有沒有接上）。新增計算機時兩個都要留。
